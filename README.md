# 餐饮商家智能经营助手 · 后端

给餐饮商家的经营后端：**用中文提问，系统把问题变成对数据库的查询、或变成对自有文档的检索，再把结果讲成人话。**

业务模块是新增的 `sky-merchant`，底座是企业级权限框架（RBAC + 数据权限）。

---

## 分支说明

一个仓库三个分支，内容互不相同：

| 分支 | 内容 |
| --- | --- |
| `merchant-agent` | **后端**（本 README 描述的这套） |
| `main` | **前端** Vue 3 + Element Plus |
| `backend` | 权限框架的课程管理练习，与本套业务不配套，可忽略 |

---

## 有什么

七块能力，都能跑、都有测试：

1. **自然语言查数据** —— 两条路线：工具调用（模型选方法）与 NL2SQL（模型写 SQL，安全边界在 AST）
2. **知识库问答（RAG）** —— 上传文档 → 父子块入库 → 检索 → 生成，答案带回可溯源引用
3. **缓存三件套** —— 穿透 / 击穿 / 雪崩，每一件都有对照实测
4. **并发扣减** —— 四种实现对照压测，结论是「条件原子 UPDATE，不用乐观锁」
5. **SQL 失败自愈** —— 执行报错原样回喂模型重写，但**校验拦下的只试一次**
6. **MCP Server** —— 手写 JSON-RPC 协议层，工具可被任意 MCP 客户端发现并调用
7. **权限体系** —— 功能权限（`@PreAuthorize`）+ 数据权限（切面），来自底座

## 技术栈

- **JDK 17 / Spring Boot 4.1.0 / MyBatis / MySQL 8 / Redis / Redisson**
- **Spring AI 2.0.1**（`spring-ai-starter-model-openai`）
  - 对话：阿里云百炼 `qwen-flash`
  - 向量：`text-embedding-v4`，1024 维
  - API Key 从环境变量 `DASHSCOPE_KEY` 读，不落配置文件
- **Druid SQL Parser** —— 把 SQL 解析成 AST 做结构化校验（随底座传递依赖，未新增）
- **MCP（Model Context Protocol）** —— 手写 JSON-RPC 2.0 协议层，**没有引入 SDK**
- JWT 鉴权来自底座，默认密钥是公开值，已换成随机串

## 能力一 · 自然语言查数据

大模型只会生成文本 —— 它执行不了代码，也拿不到业务数据。直接问「宫保鸡丁多少钱」，它会编一个数给你。

所以做了**两条路线**，安全边界完全不同：

**路线 A · 工具调用**

模型只判断「该调哪个方法、参数是什么」，Spring AI 负责真正执行。`@Tool` 方法查真实的 `tb_dish` 表，结果喂回模型组织成人话。

> **模型全程不碰代码、不碰数据库** —— 注入面在构造上就不存在。

**路线 B · NL2SQL**

模型直接生成 SQL，灵活度更高（没预定义过的问题也能问），但模型输出不可信，所以**安全边界必须放在执行前**：用 Druid 解析成 AST，过四层校验才交给执行器。

| 层 | 拦什么 |
| --- | --- |
| ① 语句类型 | 只放行 SELECT |
| ② 表级白名单 | 库里 32 张表只开放 3 张业务表（`tb_dish` / `tb_dish_flavor` / `tb_course`） |
| ③ 危险模式 | UNION / 子查询 / 注释符 |
| ④ 列级 | 禁止 `SELECT *`，列必须在白名单内 |

> **核心立场：模型是建议者，不是执行者。**
> 它被 prompt 注入绕过了也没关系 —— 只要 AST 校验不放过，SQL 就执行不了。

### 一条被 AST 拦下的越权

最初的实现只检查 FROM 子树，下面这条会**通过校验并真的执行**：

```sql
select id from tb_dish where id in (select id from sys_user)
```

隐患藏在 `WHERE` 里，不在 FROM 里。改用 AST visitor 遍历整条语句（覆盖 `SQLSubqueryTableSource` / `SQLInSubQueryExpr` / `SQLQueryExpr` / `SQLExistsExpr` 四类节点）后修复，并补上了回归用例。

**这件事的教训不是“要小心”，而是“校验必须遍历全域，不能只查你想到的位置”。**

## 能力二 · 知识库问答（RAG）

### 全链路

```
入库：文档 → 剥前言 → 切父块 → 父块落库拿 id → 每块切子块 → 批量向量化 → 子块落库
检索：问题 → 向量化 → 全量子块算余弦 → 折算父块 → 取 top-5 → 回填原文 → 按原文顺序拼上下文 → 生成 → 附引用
```

### 父子块解决的是什么问题

切分有个死结：有的问题要「长而杂」的上下文，有的要「短而纯」，**而切分是一刀切**。

父子块的解法不是让一个块兼顾两者，而是让**两层各管一头**：

| 层 | 大小 | 职责 |
| --- | --- | --- |
| 子块 | 240 字 | 被搜索 —— 小、纯，匹配得准 |
| 父块 | 300 字 | 被读懂 —— 完整，喂给模型 |

命中子块后按 `parent_id` 折算回父块：**一个父块的名次 = 它名下最优子块的名次**。

不折算会浪费名额：top-5 可能全落在同一个父块的 5 个子块上，**花了 5 个名额只拿到 1 段原文**。

### 三个刻意的取舍

**① 判「找到没找到」只用排名，不用相似度阈值**

实测同一份文档、同一个问题：无关的概述段 **0.7113**，真正装答案的那一节 **0.6270**。

如果按「相似度 > 0.7 才算相关」去筛，**会把答案筛掉、留下无关段**。

> 余弦在中文文本上挤在 0.2~0.6，与「是否相关」没有单调关系 —— 只能排序，不能卡线。

**② 入库时剥掉文档头部的「标题 + 元信息 + 导语」**

文档开头那段对**任何问题**都有一点点像，于是长期霸占检索第 1 名，把真正装答案的章节挤到第 2。

三条规则同时满足才剥（宁可不剥，也不误删正文）：以 `# ` 开头、存在 `\n## `、头部占全文不到 40% 且正文不少于 500 字。

代价说清楚：剥掉之后问「这篇文档讲了什么」这种元问题会搜不到答案。适用具体业务提问，换成产品手册 / FAQ 类语料要重新评估。

**③ 没做 rerank**

父子块 + 混合检索已经把术语型查询的 Hit@3 做到满分，rerank 的收益只剩 Hit@1 的少数几题，却要多付一次模型调用的成本和延迟。**收益不抵成本，砍掉。**

### 实测

用一份 **11290 字**的技术笔记：

| 指标 | 结果 |
| --- | --- |
| 切分 | 142 个块（52 父 + 90 子，比例 1.73） |
| 检索引擎 | 全量子块余弦（90 × 1024 维），排序确定，同问题同分数 |
| 一次提问 | 命中 5 个父块 → 上下文 **1295 字**，为原文的 **12%** |
| 输出 | 答案 + 5 条引用（chunkId / 相关度 / 原文片段） |
| 10 题评测 | **9 / 10**，平均每题 **1229 ms**（最快 496ms，最慢 2938ms） |

### 那 1 题失败的，比 9 题通过的更有信息量

评测集 10 题，唯一挂掉的是「从节点第一次连主库，日志里哪一句说明不能增量续传」。

正确答案在 3.1 节，**而 3.1 节一次都没被召回** —— 召回的 5 条全来自实验 B/C 和混合持久化那一节。

原因：**3.1 整节就是一个纯日志代码块，几乎没有自然语言**。中文问题「日志里哪一句」和一段纯英文日志之间，向量距离天然很远；而召回来的都是有自然语言描述的章节。

> **结论：RAG 对「纯代码块 / 纯日志块」是天然弱点。**
> 切分参数、top-k、rerank 都不对症 —— 问题在**块本身的语义密度**。
> 正解是混合检索的关键词路（`Partial resynchronization` 这种长英文术语，关键词能精准命中）。

判分方式也说明一下：自动判分只做「答案里有没有出现该题的关键事实」（专有名词/参数名/数字，去空格后精确包含），**不判语义等价**。所以「待复核」不等于答错，每题答案全文都会打印出来供人复核。

### 为什么不用 PGVector

评估过，但当时的现实是：本机没有 Docker / PostgreSQL，而知识库规模只有几百块 —— **全量算余弦的成本比一次网络往返还低，ANN 索引的收益是零**，引入 PG 却要多一整套运维。

所以把存储抽成接口，**换库不换算法**：

```
VectorStore（接口：只管存取，不管怎么检索）
   ├── MysqlVectorStore   ← 当前实现（向量存 TEXT，检索在内存算）
   └── PgVectorStore      ← 将来补这个，上层一行不用改
```

真正的分界线大约在**十万块**：到那个量级全扫不可接受，必须换 ANN。

## 能力三 · 缓存与并发

全部是对照实测，不是理论：

- **缓存三件套**：布隆过滤器（按 1% 误判率反推位图约 95.8 万位）+ 空值标记防穿透；互斥锁 / 逻辑过期防击穿；TTL 抖动防雪崩。
  实测 20 并发打同一热点 key：无保护时 20 次请求**全部落库**（同一毫秒），加锁后**降为 1 次**。
- **写一致性**：发现「删缓存写在 `@Transactional` 方法内」会在**事务提交前**执行，并发读会把未提交的旧值固化进缓存；改用事务提交后回调（`afterCommit`）删除，并用回滚实验验证。
- **并发扣减对照压测**：20 并发下无保护产生 **17 份超卖**，分布式锁与条件原子更新均为 0，版本号乐观锁因冲突只成功 6 次。

> 结论：**单行热点扣减用条件原子 UPDATE，不用乐观锁**。
> 乐观锁的前提是冲突少，而扣库存恰恰是同行高频冲突；且 `stock >= n` 已经完整表达了约束，再多一个 `version` 字段纯属冗余。

几种实现都在 `DishController` 上留了对照端点（`/deduct/nolock`、`/deduct/lock`、`/deduct/atomic`、`/deduct/version`），可以直接复现这个结论。

## 能力四 · SQL 执行失败的自愈

模型写 SQL 会手滑：列名拼错、表名写错、语法漏括号。以前是直接抛错，用户拿不到结果。

现在做成一个循环：**生成 → 校验 → 执行 → 读报错 → 重写**，最多 `MAX_RETRY + 1 = 3` 轮。

### 四条不能松的约束

**① 校验器拦下的 SQL，只试一次，绝不重试**

允许重试等于给模型 N 次机会去绕过安全闸门。**自愈是给「手滑」用的，不是给「越权」用的。**

**② 报错必须原样回喂**

`Unknown column` / `Table doesn't exist` / `syntax error` 三种修法完全不同。把报错概括成一句「执行失败」，模型只能瞎猜，重试就失去意义。

**③ 喂回模型的是它自己写的那版 SQL，不是校验器重写后的**

校验器会对 SQL 做改写（补 LIMIT、加数据范围条件）。喂那一版回去，模型会以为要写这么复杂的东西，下一轮越写越乱。

**④ 每一轮都要进 `attempts`，包括最后失败那次**

少记一次就说不清「试了几轮、卡在哪」。返回体里带 `attempts[]`（每轮的 SQL / 报错 / 耗时），排查不用翻日志。

### 实测：三条路径

| 场景 | 结果 | 轮数 | 耗时 |
| --- | --- | --- | --- |
| 正常问题（价格超过30的菜） | `SELECT name, price` | 1 | 576ms |
| 越权探测（查 sys_user） | 模型直接回 `NO_QUERY` | 1 | 1330ms |
| 表里没有的字段（卡路里） | 模型直接回 `NO_QUERY` | 1 | 422ms |

### 一个诚实的局限

**自愈路径实际几乎不会被触发。** `qwen-flash` 对不可答的问题会主动回 `NO_QUERY`，根本不给你「写错再改」的机会。

所以这里不声称「自愈提升了成功率」—— 没有对照组，也没有真实触发记录。要证明它有用，得用故障注入造出执行错误（比如让 schema 里出现一个库里不存在的列），那需要另做实验。

> **收获不是「实现了一个重试」，而是想明白：自愈的收益上限由模型犯错的频率决定，不由代码写得多好决定。**

## 能力五 · 把工具暴露成 MCP 服务

`@Tool` 标注的方法和 Agent 住在同一个进程里，换个 Agent 框架就作废。MCP 解决的是这件事：**给「模型 ↔ 外部能力」定一个标准接口，让 M 个客户端和 N 个工具不用做 M×N 套适配**。

### 没引 SDK，手写了一遍

```
POST /merchant/mcp      Content-Type: application/json

{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}
```

四个类，零新增依赖：

| 类 | 职责 |
| --- | --- |
| `McpTool` | 工具接口：`name` / `description` / `inputSchema` / `invoke` |
| `McpServer` | 协议层：`initialize` / `tools/list` / `tools/call` + JSON-RPC 错误码 |
| `DishMcpTool` | 具体工具，调 `IDishService`，返回**结构化数据** |
| `McpController` | 单端点收 JSON-RPC |

**加工具不用改注册代码**：`McpServer` 构造器注入 `List<McpTool>`，Spring 自动收齐。

### 协议上最容易写错的一处：错误要分两层

| 情况 | 回什么 |
| --- | --- |
| 工具名不存在、参数格式不对 | JSON-RPC `error(-32602)` |
| 工具跑了，但业务失败 | 正常返回 + `isError: true` |

**为什么必须分开**：JSON-RPC error 在多数客户端会被当成「连接故障」直接抛异常，模型根本看不到里面的文字；而 `isError: true` 的内容会原样交给模型，它才能读到「数据库连接失败」并换个策略。

另外 `notifications/initialized` 这类通知要回 **202 + 空 body** —— 回 200 带个空 JSON，有些客户端会解析失败、判定握手失败。

### 与 `@Tool` 的对照：同一份能力，两种返回形态

同一个 `IDishService`，两条暴露路径：

| | 返回什么 |
| --- | --- |
| `DishTools`（`@Tool`） | `"宫保鸡丁 38 元，在售；鱼香肉丝 32 元，在售"` —— 已组织好的中文句子 |
| `DishMcpTool`（MCP） | `{"total":2,"dishes":[{"name":"宫保鸡丁","price":38,"onSale":true}]}` —— 结构化数据 |

**跨进程时前者是错的**：调用方可能要把数据渲染成表格、只取一列算平均值、或者塞进自己的提示词模板。返回中文句子等于替它把话说死。

顺带一个工程好处：结构化数据能直接断言，自然语言只能 `contains`。

### 实测

三个方法全通：`initialize` 回协议版本与能力声明、`tools/list` 报出 `query_dish` 的完整 schema、`tools/call` 查到 3 条菜品并返回结构化 JSON。

## 接口总览

| 端点 | 说明 |
| --- | --- |
| `GET /merchant/agent/chat?message=宫保鸡丁多少钱` | 自然语言问答（工具调用路线） |
| `GET /merchant/agent/parse?message=来两份宫保鸡丁不要辣` | 结构化抽取 → `{dishName, count, spicy, packed}`，未提及的字段返回 null 而不是瞎编 |
| `GET /merchant/nl2sql/query?question=价格超过30的菜有哪些` | 自然语言 → SQL → 校验 → 执行 |
| `GET /merchant/nl2sql/agent?question=...` | 同上，但带上自愈循环（失败回喂重写，最多 3 轮），返回体含 `attempts[]` |
| `POST /merchant/mcp` | MCP 服务端，收 JSON-RPC（`initialize` / `tools/list` / `tools/call`） |
| `POST /merchant/rag/index` | 按 JSON 文本入库（`{docName, text}`） |
| `POST /merchant/rag/upload` | 上传文件入库（`multipart`，只收 md / markdown / txt，上限 512KB） |
| `GET /merchant/rag/ask?question=...` | 提问，返回答案 + 引用 + 上下文开销 |
| `GET /merchant/rag/exists?docName=...` | 这篇文档是否已入库 |
| `DELETE /merchant/rag/document?docName=...` | 删除一篇文档的全部块 |

抽取与决策分成两个入口，`/parse` 不挂任何工具 —— 避免模型在纯抽取任务里误触发查库（曾实测到该场景耗时 81 秒）。

## 关键设计决策一览

| 问题 | 选择 | 为什么不用另一种 |
| --- | --- | --- |
| 模型直接写 SQL 的安全边界放哪 | AST 四层校验，执行前拦 | 不靠提示词自律，也不靠正则（正则拦不住 WHERE 里的子查询） |
| 单行热点扣库存 | 条件原子 `UPDATE ... WHERE stock >= n` | 版本号乐观锁在同行高频冲突下成功率只有 6/20 |
| 删缓存时机 | 事务提交后回调（`afterCommit`） | 写在事务方法内会在提交前执行，把旧值固化进缓存 |
| 检索相关性判断 | top-k 排序 | 相似度绝对值无单调性，卡阈值会把答案筛掉 |
| 块的粒度 | 父子两层：子块被搜、父块被读 | 单层块无法同时满足「准」与「懂」，切分只能一刀切 |
| 向量存哪 | MySQL + 内存算余弦 | 几百块规模下 ANN 收益为零，PG 的运维成本不值得 |
| 文档头部元信息 | 入库时剥掉 | 它对所有问题都有中等相似度，会长期霸占检索第 1 名 |
| 要不要 rerank | 不做 | Hit@3 已满分，收益只在少数 Hit@1，却要多一次模型调用 |
| SQL 执行失败要不要重试 | 重试，但**校验拦下的不重试** | 允许重试越权的 SQL，等于给模型 N 次机会绕过安全闸门 |
| 工具怎么暴露 | `@Tool` 与 MCP 并存 | `@Tool` 同进程够用；MCP 让工具能被任意客户端发现，代价是多一层协议 |
| MCP 工具返回什么 | 结构化 JSON | 跨进程时返回自然语言等于替调用方把话说死 |

| `RagAskSmokeTest` | 1 | 端到端冒烟，只断言链路通、不断言答案质量 |

| `RagControllerRouteTest` | 1 | 五个接口的路由注册 |

两个刻意的分裂：

- **纯算法测试不起 Spring**（`RagRetrievalTest` 跑 0.01 秒，起 Spring 的同类要 15 秒）。打分、折算、排序是确定性的，可以测死；模型输出不是，只能断言「存在」。
- **断言只写确定的东西**：块数用区间不用精确值（切分器在边界会抖）、向量维度写死 1024、模型回答只断言非空。

> 顺带验证过一次测试有没有「牙」：把折算里的 `putIfAbsent` 临时改回 `put`，两个用例立刻红（`expected 1.0 but was 0.8` / `expected rank 2 but was 3`）。**改坏了还全绿，说明测试是摆设。**

## 怎么跑

1. **建库**：MySQL 建 `ry-vue`，依次导入 `sql/ry_20260417.sql`、`sql/quartz.sql`、`sql/rag_chunk.sql`；前端菜单需要 `sql/rag_menu.sql`
2. **起 Redis**（默认 `localhost:6379`）
3. **设环境变量** `DASHSCOPE_KEY`（百炼 API Key）
4. **改配置**：`sky-admin/src/main/resources/application-druid.yml` 里的数据库账号密码
5. **启动后端**：运行 `sky-admin` 的启动类，默认 `8080`
6. **启动前端**（`main` 分支）：`npm install && npm run dev`，默认 `80`，`/dev-api` 已反代到 `8080`

默认账号 `admin` / `admin123`。登录后从左侧「智能问答 → 知识库问答」进入，即可上传文档并提问。

## 已知问题与后续

- **检索噪声未完全消解**：概述段已通过剥前言处理，但目录、待办、更新日志这类结构性块仍可能占用排名。
- **纯代码块 / 纯日志块检索不到**：10 题评测里唯一失败的那题，正确章节整节是一段日志。向量距离对低自然语言密度的块天然不友好，**调参解决不了**，需要混合检索的关键词路或入库时给代码块补摘要。
- **自愈路径几乎不被触发**：`qwen-flash` 对不可答问题会主动回 `NO_QUERY`，不给手滑机会。要验证自愈得做故障注入，目前没做。
- **rerank 未接入**：当前决策是「收益不抵成本」，若后续要求 Hit@1 精度，这是一个明确的抓手。
- **PGVector 未接入**：接口已留，缺环境；十万块以上的规模必须换。
- **前端只做了知识库问答页**：NL2SQL 与 MCP 目前只有接口，页面未做。
- **未做流式输出**：RAG 一次提问有 5~20 秒的等待，流式能显著改善体感。
- **未做调用链追踪**：没有接 Langfuse / ARMS，模型调用的耗时与 token 只能从日志里捞。
